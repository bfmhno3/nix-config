# Repository Guidelines

This repository uses Nix flakes and Home Manager to keep reproducible user and NixOS environments consistent across hosts and operating systems.

## Project Overview

- `flake.nix` and `flake.lock` are the pinned repository entry point.
- `home/` contains reusable Home Manager modules. Keep shared defaults in `home/core.nix`. Put substantial related features behind explicit `home/<feature>/default.nix` imports. Add a feature directory only when one file is no longer clear.
- `users/<username>/home.nix` is the explicit user composition and override point. Keep user-specific values, such as Git identity, there.
- Use explicit Home Manager imports. Do not add automatic discovery, custom import libraries, deep `base`/`linux`/`darwin` layers, or per-host Home Manager trees without a demonstrated need.
- `hosts/<hostname>/` contains per-machine configuration.
- `hosts/test-vm/` is the disposable host for testing shared modules.
- `modules/` contains reusable NixOS modules extracted from `configuration.nix` or written locally.
- Every physical-host `hardware-configuration.nix` is generated by NixOS. Never edit, reformat, regenerate, or normalize one in this repository.

## Build and Test Commands

- `nix fmt <changed .nix files>` formats changed hand-written Nix files. Always pass an explicit changed-file list that excludes every `hardware-configuration.nix`.
- `nix flake check` evaluates and builds the configured checks.
- `nix build .#nixosConfigurations.test-vm.config.system.build.toplevel` builds the shared test configuration.
- `nix build .#nixosConfigurations.test-vm.config.system.build.vm` builds the terminal VM runner.
- `./result/bin/run-test-vm-vm` launches the terminal VM.
- `nix build .#nixosConfigurations.<hostname>.config.system.build.toplevel` builds a physical host. Use this only after that host is exported from `nixosConfigurations`.
- `sudo nixos-rebuild switch --flake .#<hostname>` activates a physical host. Use this only after that host is exported from `nixosConfigurations`.

## Code Style Guidelines

Use English comments that describe intent, constraints, or desired behavior. Do not narrate each operation.

NEVER try to explain HOW your code works in a comment: it's much better to write the code so that the working is obvious, and it's a waste of time to explain badly written code.

Use Nixfmt RFC style. Run the flake's `nix fmt` command before validation.

## Testing Instructions

Format only changed hand-written Nix files, with an explicit file list that excludes every `hardware-configuration.nix`. Then run `nix flake check` and build the VM with `nix build .#nixosConfigurations.test-vm.config.system.build.vm`.

Launch `./result/bin/run-test-vm-vm` and verify automatic login as `bfmhno3`. Run `whoami` and expect exactly `bfmhno3`. Run `hostname` and expect exactly `test-vm`. Run `id -nG` and verify that it includes `networkmanager` and `wheel`. Exit QEMU with the serial sequence `Ctrl-a x`.

Shared module changes require this isolated VM path. Activating a physical host is not a substitute, and testing must never edit, format, regenerate, or normalize a physical-host `hardware-configuration.nix`.

## Commit Style Guidelines

Split Git changes into atomic commits. Commit subjects must follow Conventional Commits in the exact shape `<type>(<optional-scope>): <description>`. Each commit must contain one coherent change and its directly related verification updates.

## Output

- Return code first. Explanation after, only if non-obvious.
- No inline prose. Use comments sparingly - only where logic is unclear.
- No boilerplate unless explicitly requested.

## Code Rules

- Simplest working solution. No over-engineering.
- No abstractions for single-use operations.
- No speculative features or "you might also want..."
- Read the file before modifying it. Never edit blind.
- No docstrings or type annotations on code not being changed.
- No error handling for scenarios that cannot happen.
- Three similar lines is better than a premature abstraction.

## Review Rules

- State the bug. Show the fix. Stop.
- No suggestions beyond the scope of the review.
- No compliments on the code before or after the review.

## Debugging Rules

- Never speculate about a bug without reading the relevant code first.
- State what you found, where, and the fix. One pass.
- If cause is unclear: say so. Do not guess.

## Simple Formatting

- No em dashes, smart quotes, or decorative Unicode symbols.
- Plain hyphens and straight quotes only.
- Natural language characters (accented letters, CJK, etc.) are fine when the content requires them.
- Code output must be copy-paste safe.
