# Repository Guidelines

This repository uses Nix flakes and Home Manager for reproducible NixOS hosts and user environments.

## Architecture

`flake.nix` provides one `mkHost` factory and the project template registry. Every host supplies `system`, `hostName`, `username`, `stateVersion`, `gitName`, and `gitEmail`; `extraModules` is optional. The factory injects host and identity values into NixOS and Home Manager modules. Reusable modules must not hard-code usernames, hostnames, home directories, state versions, or Git identity.

Keep the five layers distinct:

- `modules/core/` is the mandatory system core shared by every host.
- Domain-oriented `modules/desktop/`, `modules/hardware/`, `modules/network/`, and `modules/dev/` own reusable system features.
- `hosts/<hostname>/default.nix` composes system modules and contains only machine-specific behavior. `hosts/<hostname>/home.nix` explicitly composes that host's Home Manager environment.
- `home/core/`, `home/desktop/`, `home/apps/`, and `home/dev/` own reusable user-environment domains. Use explicit imports; do not add automatic discovery, custom import libraries, or deep platform layers without a demonstrated need.
- `templates/` owns project-local development shells. Compilers, build systems, and language toolchains belong in these shells rather than the global user environment.

Keep physical display topology in the owning host directory. Illogical Impulse applies `hosts/<hostname>/monitors.lua` only after its upstream configuration copy.

Every physical-host `hardware-configuration.nix` is generated by NixOS. Never edit, reformat, regenerate, or normalize one in this repository.

## Build and Test Commands

- `nix fmt <changed .nix files>` formats changed hand-written Nix files. Always pass an explicit file list that excludes every `hardware-configuration.nix`.
- `nix flake check` evaluates and builds the configured checks.
- `nix build .#nixosConfigurations.test-vm.config.system.build.toplevel` builds the shared test configuration.
- `nix build .#nixosConfigurations.test-vm.config.system.build.vm` builds the terminal VM runner.
- `./result/bin/run-test-vm-vm` launches the terminal VM.
- `nix build .#nixosConfigurations.<hostname>.config.system.build.toplevel` builds an exported physical host.
- `sudo nixos-rebuild switch --flake .#<hostname>` activates an exported physical host.

## Code Style Guidelines

Use Nixfmt RFC style. Run the flake's `nix fmt` command before validation.

Use English comments only for intent, constraints, or desired behavior. Never narrate operations or explain mechanics that clear code already expresses.

Prefer domain-driven modules and explicit imports. Add a feature directory only when one file is no longer clear.

## Testing Instructions

Format only changed hand-written Nix files, with an explicit file list that excludes every `hardware-configuration.nix`. Then run `nix flake check` and build the VM with `nix build .#nixosConfigurations.test-vm.config.system.build.vm`.

Launch `./result/bin/run-test-vm-vm` and verify automatic login as `bfmhno3`. Run `whoami` and expect exactly `bfmhno3`. Run `hostname` and expect exactly `test-vm`. Run `id -nG` and verify that it includes `networkmanager`, `wheel`, `dialout`, and `plugdev`. Verify that `command -v zsh`, `command -v tmux`, and `command -v nvim` each return a Nix profile path. Exit QEMU with the serial sequence `Ctrl-a x`.

Shared module changes require this isolated VM path. Activating a physical host is not a substitute, and testing must never edit, format, regenerate, or normalize a physical-host `hardware-configuration.nix`.

## Commit Style Guidelines

Split Git changes into atomic commits. Commit subjects must follow Conventional Commits in the exact shape `<type>(<optional-scope>): <description>`. Each commit must contain one coherent change and its directly related verification updates.

## Output

- Return code first. Explanation after, only if non-obvious.
- No inline prose. Use comments sparingly and only where logic is unclear.
- No boilerplate unless explicitly requested.

## Code Rules

- Simplest working solution. No over-engineering.
- No abstractions for single-use operations.
- No speculative features or "you might also want..."
- Read the file before modifying it. Never edit blind.
- No docstrings or type annotations on code not being changed.
- No error handling for scenarios that cannot happen.
- Three similar lines is better than a premature abstraction.

## Review Rules

- State the bug. Show the fix. Stop.
- No suggestions beyond the scope of the review.
- No compliments on the code before or after the review.

## Debugging Rules

- Never speculate about a bug without reading the relevant code first.
- State what you found, where, and the fix. One pass.
- If cause is unclear, say so. Do not guess.

## Simple Formatting

- No em dashes, smart quotes, or decorative Unicode symbols.
- Plain hyphens and straight quotes only.
- Natural language characters are fine when the content requires them.
- Code output must be copy-paste safe.
